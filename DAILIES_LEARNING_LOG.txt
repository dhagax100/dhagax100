DHAGAX DAILIES — LEARNING LOG
==============================
One file. Same name every time. Whatever you save over this replaces it
in the folder — nothing gets renamed or duplicated. New entries go at
the TOP of "Session log" below, dated, so the newest is always first.

This file is the plain-English knowledge base: rules confirmed, corrections
made, and real case studies. The code itself (with full technical detail
and code comments) is reference_daily/all_tf_combined_generator.py — this
file is the human-readable version of what that code does and why.

Every run also now produces 5m_trades_ledger.csv, one row per 5m attempt
with its stage/reason — that's the file to open first when a day's result
needs checking, before writing anything new.


DAY REPORTING FORMAT — LOCKED 2026-10-04 (this is now the ONLY way to
report the result of any day the user asks about; built and refined
live against 2025-01-02, see SESSION LOG for the full derivation)
------------------------------------------------------------------
Always a table with exactly these four columns:
  1. Control window -- the exact FROM-TO time range that control held
     one state, and what that state was.
  2. Setups allowed -- 4H/1H availability during that window, stated
     plainly (e.g. "4H sell, 1H sell" or "4H sell only").
  3. POI of interest -- ONLY the POIs that actually matter (see the
     filtering rules below). Each one named exactly: timeframe (4H/1H)
     + type (OB/RB/FVG/VI) + side (buy/sell) + origin time.
  4. Entry info -- if no entry, the EXACT reason, from this vocabulary:
     no impact / impact but body close / impact but anchor break /
     impact but swing confirmed (before trading hours, or before entry)
     / impact but trading hours finished / impact but no premium
     (discount) reached / impact but side not in control -- whichever
     applies, with the relevant time.

STRICT FILTERING RULES (user's own corrections, verbatim intent):
  - NEVER report info about a side that isn't currently allowed. If
    control is SELL, do not mention ANY buy-side POI, impact, or
    rejection at all -- not even to say it was rejected. Same mirrored
    for BUY.
  - Do not state a condition that doesn't apply. "1H not abandoned" is
    never written -- only write something when 1H actually abandons.
    Silence means normal/default; only report deviations.
  - Do not list every POI that exists or gets touched. Only list one
    if BOTH (a) its own side is currently allowed, AND (b) the specific
    resource it needs (4H or 1H) is actually held by that side at that
    exact moment -- a POI needing 1H when the other side currently owns
    the 1H slot gets dropped from the report entirely, not listed as
    "rejected."
  - NEVER report anything outside the real trading window (11:00-19:00
    Riyadh summer / 11:00-20:00 winter, from trading_window()). A POI
    that impacted and died (body close, etc.) entirely before the
    window opened is simply already breached -- it does not get a row,
    a mention, or an explanation. Control itself is still continuous
    and Daily-driven even outside the window (bias/control never
    pauses), but the per-POI setup/entry story only ever gets reported
    for what happens inside it.
  - When naming a POI's impact, always say exactly which one: "4H
    sell", "1H buy", etc. -- never just "a POI" or "the POI".

WORKED EXAMPLE -- 2025-01-02 (Daily bias SELL throughout; trading
window that day was 11:00-20:00 Riyadh, winter hours):

  Control window                              | Setups allowed              | POI of interest                          | Entry info
  11:00 (window opens): SELL                   | 4H sell, 1H sell            | none                                      | --
  13:32-13:48: SELL, 4H only (1H sell          | 4H sell only                | none                                      | --
    abandoned, PDL taken)                      |                              |                                           |
  13:48-18:27: BOTH (1H -> buy)                | 4H sell, 4H buy, 1H buy     | none                                      | --
  18:27-19:03: SELL, 4H only (anchor broke,    | 4H sell only                | none                                      | --
    buy ditched)                               |                              |                                           |
  19:03-20:00 (window closes): BOTH (1H->buy)  | 4H sell, 4H buy, 1H buy     | none                                      | --

  Result: zero entries. Every candidate that ever showed up that day
  either belonged to the side not currently allowed, or needed a
  resource (1H) the other side currently owned -- both cases dropped
  from the report entirely per the filtering rules above, not listed
  as rejections.


CURRENT RULE SET (as of 2026-10-01)
------------------------------------

BIAS
- Weekly/Daily structure sets directional control (BUY/SELL/NONE).
- 4H/1H POIs are only tradeable in the direction Weekly/Daily permits.
- Bias is EXCLUSIVELY Daily-set. Never 4H or 1H.
- LOCKED (2026-10-02, user instruction): 4H CAN now trade opposite bias
  too, same authorization path 1H already had -- a Daily POI of that
  exact opposite side impacted the SAME calendar day as this zone's own
  impact (the ARB/ORB mechanism). Previously 4H opposing was rejected
  unconditionally, no authorization path at all; that restriction is
  gone. Without same-day authorization: rejected immediately, reason
  NO_DAILY_AUTHORIZATION, for both 4H and 1H alike. Authorization lasts
  only until the authorizing Daily zone itself dies.

DAILY CONTROLLING BIAS -- the exact model (daily_controlling_bias(),
fixed through three iterations 2026-09-30, see SESSION LOG for the two
wrong versions and why each was wrong)
- Bias is CONTINUOUS -- there is no "day without a bias," ever, and no
  "undefined" state once the dataset has any real Daily event in it.
- Computed as: (1) if any Daily MSS has confirmed by the given moment,
  the LATEST confirmed MSS's direction wins, full stop -- overrides
  everything else. (2) Otherwise, the latest-impacting Daily POI that is
  classified IN-FAVOR (created_state == 0) at its own impact time wins.
  Aggressive/Old Daily POIs do NOT set or flip bias -- only in-favor
  POIs and MSS do.
- CRITICAL -- what does NOT affect bias: a POI later going invalid,
  spent, or breached does NOT blank or flip the bias it once set. Only
  a Daily MSS in the opposite direction flips bias. (User's own words:
  "the in favor... POI control creates setup not necessarily bias.")
  An earlier version of this function wrongly added a structural-
  "aliveness" check on POI candidates and was explicitly reverted after
  it broke bias continuity for 4 real days (15-18 Jan) in testing.

1H ABANDONMENT -- per-zone, bias-aware (fixed 2026-09-30; previously a
single global value per day off --default-side, which also had a
dormant bug that silently no-op'd it whenever --default-side ALL was
used -- meaning every ALL-side diagnostic run all session long had NEVER
actually applied abandonment before this fix)
- Rule (user's own words): "if we are buying today and price take
  previous daily high, 1h is abandoned for buying, the mirror is true
  for sell. period."
- Computed per 1H zone, using THAT zone's own bias at ITS OWN impact
  time (via daily_controlling_bias()) -- not one single value for the
  whole day. Handles an intraday bias flip correctly: a zone impacting
  before the flip uses the pre-flip bias/extreme, one impacting after
  uses the post-flip one.
- "Yesterday" for this check ALWAYS resolves to the last REAL TRADING
  DAY, never a literal calendar-day-minus-1 (which lands on Sunday --
  zero data -- for any Monday). Fixed 2026-09-30 after a real false
  trade (OB#131, 26 Jan) was reported and then revoked once this was
  caught; user: "Monday's yesterday is always Friday, period."
- LOCKED (2026-10-02, user-taught, now coded): PDH (BUY)/PDL (SELL)
  being "taken" is NOT a single-day fact. A wick that exceeds the
  relevant level WITHOUT a body closing through it carries forward --
  1H is pre-abandoned from the START of every following day, no fresh
  sweep needed that day, with the watched level ratcheting to each
  day's own high/low as long as that day ALSO only wicks (mirrors a
  healthy impulsive trend: candles closing past one another's extremes,
  not just wicking). Clears on EITHER (a) a real body close past the
  active level -- confirms the breakout, 1H re-armed from the NEXT day,
  or (b) a structural reversal (a day takes the OTHER side's extreme,
  confirming a swing that hands control to the opposite side or NONE)
  -- this is exactly the CONTROL strip/flip mechanism, consulted
  directly rather than re-derived. Implemented as build_pdh_pdl_chain()
  + chain_abandon_at(), replacing the old single-day find_prev_day_
  extreme/find_prev_day_sweep_time pairing in the per-zone 1H check.
  Smoke-tested 2025-01-02 to 2025-02-15: 1h_abandoned_riyadh now fires
  on 179 of 471 candidate rows (up from the old single-day check's
  count) -- mechanism is live, not yet verified against a real chart.

ZONE DISPLAY STALENESS (cosmetic only, fixed 2026-09-30, zero effect on
trading logic/ledger -- verified by full diff)
- created_state/origin is fixed at the zone's creation and never
  dynamically updated by default -- but per SPEC.md's own OOB
  definition ("a stranded, untouched opposing POI from before the
  current trend"), a zone should DISPLAY as Old once a LATER same-
  timeframe MSS confirms the opposite direction before the zone's own
  impact. Implemented as zone_stranded_by_mss() in
  weekly_combined_generator.py -- display label only, OB_STATE/
  RB_STATE/FVG_STATE classification used for trading decisions is
  unaffected.

CONTROL GATE VOCABULARY (2026-09-30)
- Day Bias: Daily-set direction, fixed for the day.
- 4H State: ARMED (in favor) or DEAD -- never opposing, ever.
- 1H State (three, priority order): OPPOSING-AUTHORIZED (a same-day
  Daily ARB/ORB impacted -- lasts until that zone dies) > ABANDONED
  (yesterday's relevant extreme got swept) > IN-FAVOR (default).
- Control Gate = 4H State + 1H State read together at a given moment
  (e.g. "4H ARMED-SELL / 1H OPPOSING-BUY").

SESSIONS / TRADING WINDOW
- THE EXACT SESSION HOURS (user's own words, 2026-09-30, "never forget
  it, never" — Riyadh clock):
    Asia:      03:00-07:00 summer, 04:00-08:00 winter
    London:    10:00-14:00 summer, 11:00-15:00 winter
    New York:  15:00-19:00 summer, 16:00-20:00 winter
- Real trading window: 10:00-19:00 Riyadh in summer, 11:00-20:00 in
  winter (London open through New York's own close, corrected
  2026-09-30 from an earlier, unverified 20:00/21:00 guess -- see
  SESSION LOG). DST-detected from real New York transition dates, not a
  hardcoded month range.
- Asia is liquidity-grab only — never an entry session.
- London/New York entries require the PRIOR session's own liquidity
  swept first (2026-09-30, user-directed) -- see session_sweep_
  satisfied() in the SESSION LOG below for the exact rule and its
  London-sweep-covers-New-York exception.
- Nothing before the window opens or after it closes counts: no setup,
  no entry, no display.
- 4H candles anchor to the same 17:00-NY forex-day rollover as Daily —
  winter grid: 01:00/05:00/09:00/13:00/17:00/21:00 Riyadh, matching the
  real FXCM/TradingView chart, not plain UTC-midnight buckets.
- Multi-day display (--since) never bridges the overnight Asia gap
  between days as if it were "in window" — each day's own real session
  is checked separately. A POI still shows if it's created in Asia but
  IMPACTS inside a real session; one that never touches any session at
  all doesn't show, on any day.

POI ELIGIBILITY
- A POI only counts if some real lifecycle event (trigger, eligible,
  impact, or breach) happens inside the window that day.
- CORRECTION (2026-09-30, user's own words: "there is no a single point
  where I said Old POIs are not to be traded... the old POIs are just
  the Aggressive POIs, period."): there is no "Old POIs never trade
  H4/1H" rule -- that was wrong and has been removed. Old and Aggressive
  are the SAME category/treatment: both trade OPPOSITE the leg/trend
  they're found in (see the Aggressive rule below), fully tradeable at
  H4/1H like any other POI, governed by the same impact-day/control-gate
  rules as everything else.
- DATA-RANGE LIMITATION: an Old POI whose own origin candle predates the
  loaded CSV (this dataset starts 2026-01-02) cannot be detected, drawn,
  or validated by the code at all -- no origin body, no anchor level, no
  way to check open-inside-zone or anchor-break for it. When one matters
  (e.g. it impacts inside a live day's window), the user supplies its
  facts by hand (side, top/bottom price, impact time) and that's treated
  as ground truth; the code cannot independently confirm or refute it.
  First real instance: 2026-01-15, an ORB (2025 origin, outside the
  2026-01-02+ dataset) impacted at 17:40 Riyadh at its top price
  1.15952 -- since it's an Old POI, per the rule above this had no
  effect on that day's 4H/1H gate (stayed 4H-SELL-only, unchanged from
  the 16:02 ARB anchor break).
- "Aggressive" POIs (AOB/ARB/AFVG) trade OPPOSITE the leg/trend they're
  found in, same family as Old POIs — an uptrend leg's Aggressive POIs
  are SELL, a downtrend leg's are BUY. Not anticipatory continuation;
  counter-trend, period.
- PREMIUM/DISCOUNT gate: the 50/50 split between the zone's
  protect_level and the most recent opposing-kind swing confirmed
  before impact. Price must have reached that midpoint before impact
  counts as a real reaction, not a random touch.

ENTRY (the real, ported rule — not the earlier simplified version)
- After impact + premium/discount confirmed: find the first confirmed
  5m swing of the SL-anchor kind ("resting" swing). That starts the
  search.
- The entry level ("candidate") is the most recent opposite-kind swing
  at/before the resting swing. It can be REPLACED by a newer swing that
  confirms before price actually breaks it — the stop order chases the
  newest swing, it's a race, not a fixed level.
- Entry fires the moment price breaks the (possibly-updated) candidate
  level.

STOP LOSS
- SL = the EXTREME (not just the most recent) of every qualifying
  SL-anchor swing between impact and the entry minute.

TAKE PROFIT
- Fixed 3R. Always.

POI VIOLATION / INVALIDATION (updated 2026-09-30 -- now FOUR triggers, not two; see SESSION LOG for each one's own fix history)
- A POI dies, in real time, the instant ANY of these four happens —
  checked on every 1-minute bar, before the entry-break test. Applies
  to every POI type (OB, RB, FVG) on its own timeframe -- never cross-
  timeframe:
    (a) h4_close -- a completed candle on the zone's OWN timeframe
        closes its BODY at or beyond the near edge of the zone (a bare
        wick doesn't count, but a close INSIDE the zone counts, not
        just fully through it). Named "h4_close" from its original 4H-
        only origin; the mechanic itself is timeframe-agnostic.
    (b) swing_break -- the zone's own protect_level (its protecting
        swing, snapshotted at creation) gets exceeded, wick or not, at
        the exact minute it happens.
    (c) OPEN_INSIDE_ZONE -- the impact candle's own open is already
        inside the ZONE (zb/zt) -- born dead. CORRECTION (2026-10-02,
        user): the check is against the POI's own zone boundaries, not
        a "candle body range" generically -- the zone itself differs by
        type: OB zone = the origin candle's BODY, RB zone = the origin
        candle's WICK, FVG zone = the GAP. LOCKED (2026-10-02, second
        correction same day): applies to OB, RB, AND FVG alike -- the
        earlier "FVG has no origin-candle concept" exclusion was an
        unexamined assumption, never actually taught; FVG zones have
        real zb/zt boundaries exactly like OB/RB, so the same
        born-dead check applies. mark_open_inside_trigger() now runs
        on engine.fvg_zones too.
    (d) swing_spent (added 2026-09-30, real ICT concept, NOT in the
        original five_bso_engine.py/SPEC.md) -- the zone's OWN
        timeframe confirms a same-kind swing (a swing HIGH for a SELL
        zone, a swing LOW for a BUY zone -- the SL-anchor kind) at or
        after impact, with NO anchor break needed. Timing matters:
        confirms before entry = entry invalid; confirms after entry =
        entry stands. Verified against RB#22 (16 Jan): swing high
        confirmed 09:39 Riyadh, over an hour before the first entry
        attempt (11:03) -- invalidating all three of that day's entries
        even though the anchor didn't break until 13:41.
- Whichever happens first (minimum timestamp across all that apply)
  kills the setup. A resting swing or entry candidate that would only
  form AFTER that moment never gets a trade -- it's a dead setup, not a
  missed one.
- CLARIFIED (2026-10-02, user): dying/going spent is PER-POI, not a
  day-level stop. A spent/dead POI simply stops producing entries
  itself -- it does NOT mean trading stops for the rest of that day.
  Any other still-alive candidate (another 4H zone armed in the same
  direction, or a fresh POI that impacts later the same day) is
  independently evaluated and still tradeable. Example: a SELL POI
  impacts, price then sweeps PDL (abandoning 1H for the rest of that
  day per the PDL/PDH rule above) and whips back up, confirming a swing
  high that spends the original POI -- that POI is done, but 4H stays
  armed regardless (PDL sweep only ever touches 1H), and any other live
  SELL candidate that day is unaffected.
- RETIRED (2026-10-02, user): the FVG "close-through" (far-edge)
  distinction from OB/RB/VI's "body-close" (near-edge) rule, previously
  tracked here as an open item, is no longer needed -- dropped. All
  three zone types use the single near-edge h4_close check.

RE-ENTRY (second entry rule)
- After a plain stop-loss exit (not TP, not still open, not a breach),
  re-arm and search again from the exact SL exit time — as long as the
  POI hasn't been structurally invalidated by then.
- The chain stops the moment an attempt resolves to anything other than
  a plain SL: a win, an open trade, or the POI dying first.
- A re-entry attempt (2nd+) that never actually became a trade is not
  reported anywhere — no row, no box, nothing. It's still used
  internally to know the chain is over, but it's not "a missed
  opportunity" worth showing.
- Open question, not yet decided for Dailies: the old OB/RB/FVG project
  found "2nd entry of a 3+-attempt POI" had a 0% win rate on that
  dataset (-12R across 12 trades) — a real reason to consider capping
  attempts. Not applied here yet; flagged for a decision.

DEDUP
- Two POIs producing the identical entry (same price, same trigger
  minute) collapse into ONE trade. One real move, not one trade per POI
  that happened to touch it.

SAME-LEG SUPERSESSION (2026-09-29)
- When a POI impacts while another same-direction POI in the same
  unbroken leg (not yet structurally invalidated) is still active, they
  are ONE opportunity, not two — cuts across zone TYPE too (an OB then
  an RB in the same unbroken move collapses the same way FVG-then-FVG
  does).
- This is a CEILING on the earlier zone's own search, not a hard skip:
  an entry it already found before the newer POI's own impact still
  stands (it already happened in real time). Only a NEW entry attempt
  starting after that moment is blocked.
- Both zones still show on the chart/table ("let them be there") — this
  only affects which one(s) get to search for a 5m entry.

CROSS-TIMEFRAME DISPLAY (2026-09-29, corrected same day)
- ONLY POI boxes and impact lines ever transfer to another timeframe —
  NEVER swing points or MSS labels, on any transfer, including 4H/1H
  onto 5m. First attempt widened Daily's entire gate (swing/MSS block
  included) to also fire on 4H/1H, which put Daily's own swing dots and
  MSS labels on the 4H/1H charts too — wrong, corrected same day, per
  the user directly.
- Daily's own POI boxes also draw on the 4H and 1H charts (Daily's own
  settings govern it, no separate toggle needed).
- 4H's and 1H's own POI boxes also draw on the 5m chart, controlled by a
  SEPARATE "5m settings" group — toggling it never silently changes
  what the 4H or 1H chart itself shows.
- Impact-line color: Daily = red, 4H/1H = green (on their own chart AND
  wherever they're projected).
- Mechanism: every timeframe's own body stays 100% natively gated
  (onD/onH4/onH1/onFive) — cross-timeframe display is built SEPARATELY,
  by extracting just the POI-box block from the source body and
  projecting it (regated, and if needed re-tagged to an independent
  settings group) onto the target chart.

DAILY SCOPING (2026-09-29)
- Daily's own POIs are scoped to the FULL calendar day (00:00-24:00
  Riyadh), not the narrow 10-20/11-21 trading window H4/1H use — a
  Daily POI can set the whole day's bias from any hour, including
  before the trading window even opens.

PARENT-POI TRACEABILITY (2026-09-29, corrected same day)
- Every impacted 4H/1H POI maps to whichever Daily POI was actually
  "active" (per same-leg supersession, above) at the moment it
  impacted — a "Daily Parent" COLUMN in the already-existing ledger
  table (the one with POI/ID/Type/Side/Bottom/Top/Origin/Trigger/
  Eligible/Impact/Status), not a separate table. First attempt got this
  wrong (built a standalone table) — corrected same day, per the user.
- The parent search itself must see a Daily POI's FULL lifecycle, not
  just what happened on today's own calendar day — a Daily POI that
  impacted on a PRIOR day and is still alive (never invalidated) is
  still the correct parent today. Fixed 2026-09-29: a snapshot of
  Daily's zone lists is taken BEFORE the calendar-day filter trims them,
  and that snapshot (not the filtered engine) is what the parent search
  uses.

MULTI-DAY VIEW (2026-09-29)
- --since START (with --show-date END) shows the WHOLE continuous run
  from START through END in one chart/ledger — every swing, MSS, POI,
  setup and entry from every day in between, not one day at a time.
  Trading forward: keep --since fixed at day one, just move
  --show-date/--as-of forward each new day. Omit --since and behavior
  is exactly the single-day behavior --show-date always had.
- The entry-search itself still respects each day's OWN real session
  hours even across a multi-day range — Asia (or any off-hours minute)
  can update structure (candidate replacement, invalidation) but can
  never itself trigger an entry, on ANY day in the range, not just the
  first.
- Output filenames are ALWAYS the same fixed set, overwritten in place
  — never a dated/per-day copy. One pine file, one ledger, period.

CROSS-DAY CANDIDATES / "REACT DAY" (2026-09-29)
- A 4H/1H POI that impacted on a PRIOR day and is still alive (not yet
  structurally invalidated) is still a real candidate for TODAY, not
  just Daily. Previously, filter_to_date()'s narrow window trimmed
  these zones out of engines["h4"]/["h1"] entirely before
  compute_5m_trades ever saw them — so a still-alive POI carried in
  from yesterday silently produced zero 4H/1H setups today, with no
  reason recorded anywhere. Fixed: compute_5m_trades now searches the
  FULL, unfiltered zone history (bounded only to "impacted by today's
  close, not already structurally dead before today's window opened" —
  a real ledger stage, DEAD_BEFORE_WINDOW, records exactly why a
  carried-in zone is excluded).
- A carried-in zone's own entry SEARCH still only starts at today's own
  window open — it never re-discovers and re-reports an entry a PRIOR
  day's own run already found and resolved. Only the zone's continuing
  ELIGIBILITY (impact, protect_level, invalidation) carries across the
  day boundary, never its already-settled trade history.
- "React day" rule (taught by the user, 2026-09-29): the day after an
  "impact day" (yesterday wicked/reacted off an in-favor POI and closed
  off it) is a react day. Today keeps looking for BOTH 1H and 4H setups
  in the same direction, AS LONG AS today hasn't taken out yesterday's
  relevant extreme (the low, for a SELL bias; the high, for a BUY
  bias). The moment today sweeps that extreme, 1H setups are abandoned
  for the rest of the day and only 4H stays in play. Automated the same
  day: the sweep, if any, is detected from the real Daily bars and real
  M1 data (not asserted), and acts as a ceiling on 1H searches only —
  same treatment as same-leg supersession, so a 1H entry already found
  before the sweep still stands. Ledger column: h1_abandoned_riyadh.
- LOCKED (2026-10-02, user instruction): this same PDL/PDH sweep check
  now applies on the IMPACT DAY itself too, not just react/continuation
  days -- it can happen at any minute of the impact day (checked over
  the full calendar day, same as every day), and must not be overlooked.
  The 2026-09-29 is_react_day() gate that deliberately skipped this
  check on a zone's own impact day is removed (function deleted, now
  unused) -- the sweep check runs unconditionally for every in-favor 1H
  zone, every day, impact day included. If yesterday's relevant extreme
  is already swept by the time a zone impacts today, 1H is abandoned
  from that moment forward the same as on any other day.
- CLARIFIED (2026-09-30, user's own teaching): "continuation day" is NOT
  a separate mechanic from "react day" -- it's the same rule, just
  further down the same unbroken trend. is_react_day()'s real condition
  is "no same-side Daily POI impacted TODAY" -- that stays true every
  single day the trend runs (day 2 after impact, day 5, day 20 --
  doesn't matter), not just the literal day right after impact. So the
  low/high-sweep check (find_prev_day_extreme + find_prev_day_sweep_time
  -> h1_abandon_at) already runs, unchanged, on EVERY continuation day,
  compared against YESTERDAY's own extreme each time (not the original
  impact day's extreme) -- no separate code path needed, this was
  already correct. In plain terms: every day the trend continues with
  no fresh same-side Daily impact, ask one question -- "has today swept
  yesterday's relevant extreme yet?" -- checked against the FULL
  calendar day (a sweep can happen before the trading window even
  opens, at any minute). Not yet -> both 4H+1H stay armed in the trend
  direction. The moment it happens (whatever minute that is) -> 1H is
  abandoned for the rest of that day, 4H only, from that exact minute
  forward. "React day" and "continuation day" are the same word for the
  same thing; use either, they mean one mechanic.
- CLARIFIED (2026-09-30, user's own words: "if we said we are sell on
  4H, why do we need any 4H BUY POI or story, that is ridiculous?"):
  4H NEVER trades the side opposite the day's controlling bias. There
  is no "opposing 4H" concept, period -- 4H has exactly two states each
  day: armed in the trend direction, or abandoned (NONE) once
  structurally invalidated. A 4H zone of the opposite side is never a
  real candidate, never needs "dealing with," and isn't part of any
  story -- ignore it outright, same as the code's own compute_5m_trades
  already does when side is pinned to one direction (--default-side
  SELL/BUY filters out the opposite side's zones at BOTH 4H and 1H
  before any entry search runs). Only 1H can ever widen to the opposing
  side -- via a valid Aggressive/Old POI impacting on ITS OWN impact

2026-09-28 — First full case study: 12 January 2026, real data
- Bias: SELL. Window: 11:00-21:00 Riyadh (winter).
- 7 POIs alive in the window. Only 2 (OB#44 + RB#67, same
  protect_level, impacted a minute apart) produced a trade — deduped
  into one: SELL entry 14:32 @ 1.16847, SL 1.16892, TP 1.16712.
- REAL OUTCOME: stopped out at 16:08. A loss, -1R (4.5 pips risked).
  Confirmed by simulating forward through the actual M1 data to the
  real exit, not assumed.
- The POI was structurally invalidated (protect_level broken) at the
  SAME minute the SL was hit — 16:08. Because of that, the re-entry
  chain correctly refused to re-arm: the setup was already dead the
  instant it lost. This is the invalidation gate doing real work on
  real data, not just theory.
- Why the other 5 POIs never traded:
  - RB#68 (SELL, impacted 16:07) — invalidated at 16:08, one minute
    later. Never had time to form a resting swing.
  - RB#69 (BUY, impacted 17:25) — invalidated at 17:29, same pattern.
  - FVG#9 and FVG#31 (both BUY) — never reached the premium/discount
    midpoint before their own impact. Not a bias-filter exclusion —
    these failed on their own structural terms.
  - OB#45 (BUY) — never impacted at all.
- Lesson: most POIs in a window die fast. Impact alone means nothing —
  the premium check and the invalidation clock start racing
  immediately, and most setups lose that race before a trade is even
  possible. A POI whose protect_level sits very close to its own likely
  entry/SL should be treated as fragile going in, not as strong
  confirmation just because it impacted.
